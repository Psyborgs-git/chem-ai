- **实测结果(Xeon 8375C 8C/31.3GiB,Postgres 16.10)**:

### 发现并修复的缺陷(由基准实测暴露)

- **`run_parse` 管道缓冲死锁**(`workers/ingestion/runner.py`):旧实现先 `proc.join()` 再读结果队列;pickled `ParseReport` 超过 OS pipe buffer(~64 KiB,约 >400 行 CSV)时子进程阻塞在 flush、join 永不返回,被误判为 `PARSE_TIMEOUT` 导致批次 quarantine。实测修复前 600 行死锁 60 s,修复后 0.2 s 解析出 1200 records。修复改为在 join 期间持续 drain 队列,并在子进程退出后再做一轮短宽限 drain(队列 feeder 线程可能比进程退出晚一拍投递,竞态下被误判 WORKER_CRASH);timeout/kill 语义不变。回归测试 `test_large_report_crosses_the_pipe`,10× 重复跑 110/110 绿。

### 2. 分页/流式/导入背压与命令预算核对

- keyset 游标遍历 300/1200 行均正确走完(`assert seen == N`、`assert recordCount == rows*2`),无跳页;工件下载哈希校验通过;导入未绕过同步上限。发现一项如实记录的限制:导入在请求路径内同步执行,600 ms 导入期间并发 `/healthz` 探针等待 ~595 ms —— 在 §23.1 预算内但值得跟进(建议把 `artifactImport` 移入 run queue/worker thread),已写入报告“Limits”。

## 已知限制

- 基准为本机 loopback 单客户端实测,不外推为用户机器吞吐;不同硬件不可直接对比(报告已声明)。
- 导入在请求路径内同步执行:600 ms 导入期间并发 healthz 探针等待 ~595 ms(仍在 mutation-ack 预算内);更大导入会拖住整个单进程 API —— 建议后续把执行移入 run queue(报告“Limits”已记录,未在本 ticket 改架构)。
- 词法搜索 corpus 为 1200 条单 cell chunk;embedding 检索尚未实现故未测。
- 主题持久化用 cookie 而非浏览器存储(§8.2):跨域共享同一 origin 即可,默认容量/过期 1 年;无跨设备同步。
