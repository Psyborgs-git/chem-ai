## 实现内容（按缺陷逐条）

### 缺陷 1 — 导航 `/materials` `/models` `/settings` → "Page not found."

常驻导航（`AppRoutes.tsx` `NAV`）声明了三个没有 `<Route>`/页面的入口。
按 ticket 指引逐一核实后如实处理：

- `/models`：`features/learning/models/ModelsPanel.tsx` 是 CS-0802 已交付
  的模型注册面板，此前从未路由 —— 挂载 `ModelsPage` 于 `/models`，以
  `taskId={null}` 调用（后端 `modelReleases`/`trainingRuns`/
  `sessionModelPins` 均接受 `task_id: GlobalID | None`，即全 workspace
  视图）。`learning/training/TrainingPanel.tsx` 已刻意内嵌于
  `TaskWorkspace` 的 `training` section，不另挂路由。
- `/materials`：`features/materials/` 仅有 `operations.ts`（9 个
  mutation）+ `index.ts`，**无任何 import 方**，schema `Query` 亦无
  材料列表查询 —— 这些操作属于任务流内嵌能力，没有独立页面可挂载。
  按规则移除导航链接，不虚构 materials catalog。
- `/settings`：无任何 settings surface（CS-0506 已记录无 connector UI）
  —— 移除导航链接，不建设置页。

同时把路由树移入 `ShellContent`（`QueryBoundary` 按 `pathname` 作 key），
使单页查询失败不再把错误边界卡死在所有路由上 —— 导航换页即重挂载。

### 缺陷 2 — `/compute/fallback/<bad-id>` 误渲 "Not signed in"

根因：`QueryBoundary` 是单一 `failed` 布尔态，对**任何**捕获异常一律
渲染 `Not signed in`；而 Relay 在 `response.data == null` 时抛出
`RelayError`（`error.source.errors` 携带服务端 typed `CODE: message`）。

修复（`AppRoutes.tsx`）：

- 新增 `queryErrorMessages`/`classifyQueryError`：从 `error.source.errors`
  提取 `CODE:` 前缀分类 —— `UNAUTHENTICATED`→auth、`FORBIDDEN`→
  forbidden、`NOT_FOUND`/`VALIDATION`/GlobalID base64 解析错→
  not_found、其余→unknown。
- `QueryBoundary`（shell 级）按分类渲染：仅 auth 才显示 signed-out；
  forbidden→`ForbiddenState`；其余→如实 `ErrorState`（带服务端 detail）。
- `FallbackPage` 改为自带 `FallbackQueryBoundary` + `Suspense`：
  not_found 分类渲染 `<EmptyState title="Run not found." />`。
- `FallbackPage` 增加 `isRunGlobalId` 预检：param 先 `decodeURIComponent`
  再 `atob` 解码，要求形如 `Run:<uuid>` —— 不能解码成合法 GID 的输入
  直接走 not-found，不发查询；能解码的交给查询，由边界分类兜底。
  （`runFallback` 在 schema 中为 non-null `JSON`，所以任何字段错误都会
  使 `data` 归 null → Relay 抛出 → 边界必然接管，无中间态。）

配套后端修复：`strawberry.Schema` 增加 `DomainErrorExtensions`——此前
`DomainError` 逃出 resolver 后 wire 层 `errors[]` 只带 `args[0]` 文本
（graphql-core 不取 `__str__`，`extensions` 为空），NOT_FOUND 与鉴权
失败对客户端不可区分。现在 `errors[].extensions` 携带完整 §8.3 契约
（`code`/`fieldPath`/`retryable`/`safeDetails`）；前端分类优先读
`extensions.code`，message 文本仅作无 code 错误的兜底。

### 缺陷 3 — candidate/import 列表 mutation 后不刷新

先纠正一个仓库级误解：`useLazyLoadQuery` 的查询结果以
(operation, variables, fetchKey) 为键缓存 —— **组件 `key` 重挂载不会
重新发请求**（e2e 实测：remount 后页面仍显示缓存的空列表，无第二次
网络请求）。真正的刷新约定是 `fetchKey` + `fetchPolicy: "network-only"`
（`RunsPanel`/`CloseoutPanel`/`ResearchPanel` 已在用）。

- `CandidatePanel`：`ProposeForm` 新增 `onProposed` 回调，propose 成功
  后 `setFetchKey(+1)`；`CandidateList` 的 `useLazyLoadQuery` 增加
  `{ fetchKey, fetchPolicy: "network-only" }` —— propose 后原地刷新。
- `ImportReview`：`BatchList` 的 `key={reloadKey}` 重挂载改为
  `fetchKey={reloadKey}` + `network-only` —— 顺带保留 `selected`
  批次选中态（重挂载原会把选中态一并丢掉）。
- `RecordRow` promote：新增 mutation `updater`，仅在
  `recordPromote.claim != null`（成功）时把该 record 的 `status` 写为
  `accepted` —— 与服务端 `promote_record` 事务内 `record.status =
  "accepted"` 的确定性转换一致，行级状态无需 reload 即正确。
  （`recordReview` 返回 `record { id status }`，Relay 已自动归一化，无需
  额外处理。）
- `ModelsPanel` 同样存在该潜在缺陷（`key={refreshKey}` 重挂载 +
  `network-only`，register/rollback 等 mutation 后列表不会真正
  重取）——同类缺陷一并修复：PointerCard/ReleaseList/PinList 改为
  `fetchKey` prop + `network-only`。

### 缺陷 4 — `contractFreeze` 瞬时 null flake

调查结论：`contractDraftCreate`/`contractFreeze` 仅把 `DomainError`
转换为 typed `errors[]` payload；任何非领域异常（如并发
`draft_contract` 的 `max(revision)+1` 撞 `(task_id, revision)` 唯一约束
产生 `IntegrityError`、序列化冲突、commit 时连接中断）都会向上逃逸 →
GraphQL `errors[]` + `contractFreeze: null` —— 正符合“null、重试即成
功”的 flake 签名。两层加固（非 sleep/retry hack）：

- `TaskService._task` 新增 `for_update` 参数；`draft_contract` 与
  `freeze_contract` 改为 `SELECT … FOR UPDATE` 锁住任务行 —— 同一任务的
  contract 写操作在 DB 层串行化，`max+1` revision 分配与 `version`
  递增不可能再交叠撞唯一约束。
- 两个 mutation 入口增加 `except SQLAlchemyError` → 回滚并返回
  `CONFLICT / retryable=true` 的 typed 错误 —— 瞬时持久化失败从此是
  可重试的协议错误，而非裸 `null` 字段。

（UI 侧无 `contractFreeze` 按钮，该路径为 console/API-only —— flake
只可能来自服务端提交阶段，故加固在服务端。）

typed 成功，无 null 字段。

- `contractFreeze` flake 在本机未能直接复现 —— 修复针对最可能的
  null 路径（非领域异常逃逸 + revision 竞争），读写两侧均已加固；
  AT-1201-4 验证并发 draft 序列化而非 flake 本身。

  空态），e2e 仅断言真实 surface 在场，不虚构数据。
- materials mutation 集合本可支撑 list 页面，但既无列表查询也无任何
  使用方 —— 本 ticket 按“移除死链”处理；若未来补建 materials
  surface，再恢复导航。
- `key`-remount 不刷新 useLazyLoadQuery 的 Relay 语义已在本文件
  纠正；仓库中其余 `fetchKey` 约定面板（RunsPanel/CloseoutPanel/
  ResearchPanel）本已正确，未改动。
