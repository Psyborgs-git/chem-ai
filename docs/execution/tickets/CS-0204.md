# CS-0204 — Implement formula/process/candidate revisions

**Status:** completed
**Phase:** P02 · **Owner:** controller

## Changed files

- `services/studio-api/src/studio/persistence/models.py` — five new
  workspace-scoped tables:
  - `FormulationFamily` — the lineage revisions hang off.
  - `FormulationRevision` — draft → accepted → superseded revision
    with `payload` (ingredient lines as Quantity DTOs,
    `amountBasis`, `declaredTotal`, `tolerance`, `completeness`,
    `processRevisionId`, context fields, `validationFindings`),
    `content_hash`, parent link. Guarded by
    `cs_revision_guard('family_id')`.
  - `ProcessRevision` — ordered steps with inputs/outputs,
    conditions (unknown stays unknown), equipment, source,
    approval status; same guard. Formula and process version
    together but remain distinct objects (§5).
  - `CandidateRevision` — task-scoped revision with
    `entity_kind` (`formulation|molecule|material`), entity
    revision ref, parent/branch link, hypothesis, payload
    (`proposedDifferences`, `evidenceIds`), contract-revision link,
    `status` (`draft|submitted|accepted_for_research|rejected`)
    and `eligibility` (the five §7.2 values) as a *separate
    column* — eligibility is an assessment axis, not content.
  - `CandidatePatch` — `proposed|accepted|rejected` proposal with
    patch ops, proposer kind, reviewer + `rejection_reason`
  retention.
- `services/studio-api/migrations/versions/0007_formulations_candidates.py`
  — same shape in SQL; adds `uq_contract_revisions_scope_id` to
  `success_contract_revisions` (CS-0101 gap found by the composite
  FK); attaches the generic guard to formulation/process revisions
  and a **dedicated `cs_candidate_revision_guard`** to candidates:
  `accepted_for_research` freezes every content column while still
  allowing `eligibility` (and terminal status) to move — matching
  §7.2 "accepted content is immutable; eligibility is separate".
- `services/studio-api/src/studio/domain/materials/formulations.py`
  — `FormulationService`:
  - `draft_revision` — parses every ingredient amount through
    `Quantity.from_dto` (malformed DTOs rejected at the boundary),
    records non-blocking `validationFindings` (missing amounts,
    invalid amounts, fraction outside [0,1], duplicate identity
    lines — flagged, *never* summed, total outside tolerance).
    Incomplete drafts may sit above/below their stated total.
  - `accept_revision` — the declared-basis gate: requires
    `completeness == "complete"`, runs `check_declared_total`
    against the revision's own `declaredTotal`/`tolerance` →
    `COMPOSITION_TOTAL_INVALID` on mismatch, **values are never
    normalized** (AT-0204-1). Supersedes the prior accepted
    revision through the guard's only legal transition.
  - `draft_process_revision` / `accept_process_revision` — step
    order stored verbatim; unknown conditions stay marked.
  - `find_duplicate_formulations` — groups revisions by
    `ingredient_key` (order-*independent* ingredient identity hash)
    and reports each member with its `process_signature`
    (order-*significant* step hash). Same ingredient set +
    different process order → one group, two distinct signatures,
    nothing merged (AT-0204-3).
- `services/studio-api/src/studio/domain/candidates/service.py` —
  `CandidateService`:
  - `create_candidate` (`propose_candidate` — agents may propose),
    `submit_candidate`,
    `review_candidate` (human `review_science` →
    `accepted_for_research|rejected`),
    `set_eligibility` (human; moves the eligibility column even on
    accepted rows — the guard permits it),
    `propose_patch`, `review_patch` — reject retains
    `rejection_reason` and never touches the target's content
    (AT-0204-2); accept materializes a *new* draft
    `CandidateRevision` (parent-linked, revision+1) so the target
    row itself stays immutable. Patch ops are an explicit
    key→value map; they may not overwrite `payload`/`status`/
    `eligibility`/`revision`.
  - Audit + outbox records on review and patch apply.
- `services/studio-api/src/studio/domain/candidates/__init__.py` —
  exports.
- `services/studio-api/tests/integration/test_formulations_candidates.py`
  — 9 integration tests.

## Acceptance mapping

- **AT-0204-1** (mass fractions totaling 1.2 →
  `COMPOSITION_TOTAL_INVALID`, no normalization):
  `test_reject_normalized_never` — acceptance raises the typed
  error, the row stays `status: "draft"`, and stored amounts read
  back `"0.6", "0.6"` — not normalized to 0.5/0.5.
  `test_valid_total_accepts` proves the gate admits a conforming
  revision; `test_incomplete_draft_keeps_findings_without_blocking`
  proves a draft records `total_outside_tolerance` as a finding
  and cannot be accepted while incomplete;
  `test_duplicate_lines_flagged_not_summed` proves duplicate
  identities are flagged with both lines preserved.
- **AT-0204-2** (rejected patch → content unchanged, reason kept):
  `test_rejected_patch_retains_reason` — after rejection the
  candidate's payload and `content_hash` are byte-identical, no
  new revision exists, and the patch row retains
  `rejection_reason`. `test_accepted_patch_creates_new_revision`
  covers the accept path (new parent-linked draft revision,
  original untouched).
- **AT-0204-3** (equivalent ingredients + different process order
  → process differences preserved):
  `test_process_order_survives_dedup` — two families with the same
  ingredient set land in one `ingredient_key` group; their
  `disperse→bake` vs `bake→disperse` processes produce two
  distinct `processSignatures`, and both revisions remain.

## Limitations

- Dedup is *exact* ingredient-set grouping; near-duplicate
  grouping (equivalent grades, alias-aware identity) is a separate
  operation per §6.2 and lands with the review-workflow UI.
- Formulation payload validation flags other-basis amounts but a
  full "imported-other-basis → reviewed transform" workflow is
  surfaced with the transform UI — the data model already keeps
  the faithful import and its findings.
- No GraphQL surface yet — candidate formulation screens arrive
  with the task-workspace UI (CS-0206); resolvers will sit on top
  of these services unchanged.
- `candidate_revisions` is revisioned per *task*; cross-task
  candidate lineage uses `parent_revision_id` chains within the
  same task.
