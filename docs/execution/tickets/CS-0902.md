## 实现内容

### 1. `packages/engine-adapters/rl/` — RL 训练适配器

- `contracts.py`：纯 pydantic（`extra="forbid"`）——
  `RlTrainSpec`（algorithm/model/optimizer/rollout/rollout_budget/
  checkpoint/max_steps/seed/corpus_digest/resume + 钉死的
  `env_contract_version`/`reward_contract_version`——run 内版本
  冻结；`digest()` 绑批准）；`RlModelSpec`（`RL_MODEL_LICENSES`
  白名单内 `license_id` 才允许训练——unknown license 在 spec
  校验即拒）；`RlAlgorithmSpec`（`family="grpo"`；
  `beta` 定死 0.0——本环境无 reference 模型通道，非零 beta
  **拒绝而非静默忽略**）；`RlOutcome`/`RlCheckpoint`/
  `RlParameterProof`（adapter 前后 sha256 变化 ∧ frozen
  backbone sha256 不变——真实优化器步进证据）/
  `RlTrainingLabels`（capability 标注：fixture_only /
  not_validated / execution=cpu / gpu=false）。
- `pico_rl.py`：HF 兼容 pico backbone（CS-0801 PicoGPT-class，
  字符级 tokenizer + `PreTrainedModel`/`GenerationMixin`
  适配）——U08 GPU 未知 → CPU 兼容微模型，诚实标注
  fixture；`state_dict_sha256` 供参数证明。
- `rollout.py`：episode 驱动——**policy 动作=候选标记采样**：
  对每个候选动作做 teacher-forced 标记 logp 打分→softmax→
  `torch.multinomial` 采样→marker token 记入 completion
  （携带采样 logprob + env_mask=1）→ `env.step()` 真实环境
  反馈→观察 render 以 env_mask=0 追加。episode 预算受
  `RolloutScheduler` 并发上限 + 任务/包络预算双重约束。
- `rollout_plan.py`：确定性 rollout 计划（每步每 task 的
  episode 种子/计数——按 spec+seed 重放可复现）；
  `corpus_digest(tasks, snapshot, policy)` 字节级规范化 sha256。
- `trainer.py`：`train(request, output_dir)` —— TRL **GRPOTrainer**
  真训（`use_cpu=True`，LoRA via peft；reward_fn 调
  `RewardService.score_episode` → components/gates 逐 episode
  落 `rewards.jsonl` + `episodes/`，train.jsonl 为真实训练
  telemetry）；resolved `config.json` 先写盘再跑（同 SFT 约定）；
  HF checkpoint → meta.json + `RlCheckpoint` 列表（scratch 相对
  路径，与 domain harvest 前缀一致）；`resume/` 目录注入 →
  `trainer.train(resume_from_checkpoint=…)` 真续训；
  `CANCEL` 哨兵 → `should_abort` → `incomplete_run`
  （usable=false）；structured `{code,message}` 错误出口。
- **算法选型记录**（§19.1）：pinned TRL 版本提供的 on-policy
  算法族中，本环境 action 空间为**离散候选标记 + 组内
  comparative reward**（同 task 多次 rollout 取组归一优势），
  与 GRPO 的 grouped advantage 原生匹配；PPO 需 value head +
  KL ref（本环境无），离线算法（DPO/KTO）不消费 on-policy
  episode reward——故选 GRPO（TRL `GRPOTrainer` +
  `rollout_func` 自定义环境 rollout），默认 `loss_type=dapo`、
  `scale_rewards=group`、`importance_sampling_level=token`。

### 2. `workers/training/rl/` — corpus + 隔离训练器

- `corpus.py`：approved corpus 构建——`parse_corpus` 产出
  （tasks + `EvidenceSnapshot` + `RlPolicyRef`），任务
  `task_id` 去重、`corpus_digest` 与 spec 双向校验（批准绑定
  的字节在 runner 端重算——篡改即 `ENGINE_UNSUPPORTED_INPUT`）。
- `trainer/Dockerfile` + `requirements.lock`：pinned 运行时
  （torch CPU + trl + peft + transformers + datasets 全钉版），
  `HF_HUB_OFFLINE=1`、非 root、read-only root、入口
  `runner.py`。
- `trainer/runner.py`：容器内引擎入口——读 stdin request
  `{spec, corpus}` → 版本断言 → corpus digest 重算 →
  `train()` → result.json 落盘；`{code,message}` JSON 错误。
- `trainer/runtime.py`：`IsolatedRl` host 侧——`docker run
  --network none --read-only --cap-drop ALL` + 资源上限
  （cpus/memory/pids 取自 spec `rl_envelope`），挂只读输入 +
  scratch 卷（train.jsonl/rewards.jsonl/episodes/checkpoints/
  adapter/result.json 字节级 harvest）；镜像缺失 → 诚实
  `ENGINE_UNAVAILABLE`（engine 测试按 image 存在与否 skip，
  **不挡单测/契约/集成**）；无 GPU 请求路径、无 cloud
  fallback（P10 仍禁用）。

### 3. `services/studio-api/.../learning/rl.py` — 运行生命周期 + gate 接线

- `RlTrainingService`：`create`（CAP_MANAGE_MODELS + spec 校验
  + corpus digest 绑定）→ `submit` → `approve`（server-side
  `CAP_APPROVE_MODEL`——**agent 主体不可批准**，capability
  检查永远 server-side）→ `queue` → `execute`（scheduler
  分派 → `IsolatedRl.train` → artifact harvest →
  `_persist_run_artifacts`：episodes/rewards/checkpoints/
  telemetry/adapter 全部入 vault-confidential blob + 溯源）→
  `transition`（`CAP_REVIEW_SCIENCE` → CS-0803
  evaluation→promotion gate 复用：候选须过独立评测对比，
  `last-good supervised release` 不受影响）。
- `cancel`/`resume`：取消经 `CANCEL` 哨兵传入容器 →
  `incomplete_run` 可 `resume`（resume_from 指向已持久化
  checkpoint + optimizer 状态，目录字节回灌）。
- `_envelope`：compute/steps/rollout 预算包络——任一耗尽 →
  `budget_exhausted` 终止（**scheduler/budget 层停止工作，
  无 fallback**）。
- capability 标注 `_capability_labels(image_available=…)`：
  image 缺失时 run 仍可建/批准/排队但 execute 诚实失败，
  标注恒 `dataStatus=fixture_only` / `scientificStatus=
  not_validated` / `gpu=false` / `execution="cpu"`。

## 已知限制 / 能力声明

- **capability 标注**（与 CS-0801/0901 同口径）：一切产出恒带
  `dataStatus=fixture_only`、`scientificStatus=not_validated`、
  `gpu=false`、`execution="cpu"`、`heldOutSuiteAccess="none"`——
  pico backbone + fixture corpus 的 reward 爬升**不构成科学
  验证**；telemetry=训练 telemetry，非能力声明。
- **U08 未知 → CPU**：模型为 PicoGPT-class 字符级 fixture
  （`pico-rl-v1`），LoRA adapter 为唯一可训练参数面——
  backbone frozen（参数证明里 sha 必须不变）。GPU 镜像/
  调度属后续票据，本票无 GPU 请求路径。
- **beta 定死 0**：环境无 reference-model 通道（无 held-out
  权重访问）；非零 beta 在 spec 校验直接拒——不是默认 0。
- **预算耗尽 = 停止而非降级**：compute/steps 任一耗尽 →
  `budget_exhausted`；P10 cloud fallback 按设计仍禁用，
  代码内无 fallback 路径（security 测试做源码级断言）。
- **held-out 套件不可作为奖励**：reward_fn 只调
  `RewardService.score_episode`（CS-0901 冻结组件/gates）；
  evaluation/promotion 路径与 reward 路径代码级隔离。
- **rollout 并发**由 `RolloutScheduler`（spec
  `max_concurrent_rollouts`）+ 域 `_envelope` 双层约束；
  engine 内 episode 顺序执行（bounded），并发上限为域侧
  scheduler 语义。
- **resume 语义**：`resume_from` 指向 vault 持久化的
  checkpoint 目录（adapter+optimizer bytes 回灌）；
  HF checkpoint meta.json 带 configDigest——跨 spec
  resume 在 runner 端拒。
- CS-0903（更大规模训练循环编排）与 CS-0506（U16）明确未做；
  P10+ 云 fallback 按设计仍禁用。
