## 实现内容

### `infra/cloud/providers/cloud_providers/` — 机密执行适配器（~700 行）

- **`types.py`**：`ApprovedEnvironment`（批准的环境身份 + §20.4 全量
  策略断言——measurement/firmware/GPU 机密覆盖/image_digest/
  model_digest/network/operator_access/telemetry/content-logging/
  ephemeral-credentials/private-artifacts/TTL 上限/deletion/
  synthetic_only/approval expiry）；`AttestationDocument`
  （provider 供给的证据，`signature`=canonical digest 防篡改）；
  `AttestationVerdict`（verified/refused + per-check 明细，
  fail-closed）；`ApprovalRef`（owner 批准引用：digest/approver/
  capability/bound/expiry）；`KeyReleaseRequest/Ticket`
  （ephemeral job-scoped）；`ConfidentialJobSpec`（provenance
  synthetic|approved_real）；`ImportedArtifact(s)`（恒
  confidential+untrusted+unvalidated）；`ProviderObservation`；
  `StorageVerification`；`ConfidentialReconcile`。
- **`attestation.py`**：`verify_attestation` 全或无校验器——18 项
  独立具名 check（签名/双端 expiry/identity/measurement/firmware/
  GPU 覆盖/image/model digest/network/operator/telemetry/
  content-logging/ephemeral/private-artifacts/issue-time 合理性）。
  任一失败即 refused——**缺失证据同样拒绝**（provider 不报 GPU
  覆盖 → fail closed，§20.4 "unavailable coverage fails closed"）。
- **`adapter.py`**：`ConfidentialExecutionAdapter` 同时实现
  `CloudProvider`（broker 的 submit/status/cancel/delete/
  drain_callbacks 面）与机密执行面（`attest`/`release_key`/
  `submit_confidential`/`reconcile`/`verify_storage_deleted`/
  `import_outputs`/`observation`）。`submit()` 先校验 recipient==
  批准环境 → `release_key` **内联重验 attestation**（调用方传入的
  verdict 永不信任，伪造/过期 verdict 无法换出密钥）→ 构造
  synthetic provenance job spec → backend。`import_outputs` 拒绝
  非 private/超 TTL artifact；`reconcile`+`verify_storage_deleted`
  诚实报告 provider 侧保留字节。
- **`backend.py`**：`ConfidentialBackend` 协议——真实 provider 的
  插点（attestation_document/release_key/submit_confidential/
  生命周期/import_outputs/retained_bytes 探针）；`kind` 诚实标注
  `"synthetic"|"live"`，double 永不能报 live。
- **`double.py`**：`ConfidentialDouble` 进程内后端——自铸 attestation
  文档（`attestation_mode`: present/missing/tampered/expired +
  `doc_overrides` 逐项打错），honest 记录 released_keys/received/
  confidential_jobs/outputs；生命周期复用 `ProviderDouble`
  （`_ConfidentialJobRunner` 子类令 handle.provider=
  confidential-double，broker 的 cancel/delete 按名解析）。
- **`registry.py`**：`register(spec, approval, backend)`——缺批准/
  过期/非 approve_export capability/批准主体不匹配均拒绝；空注册表
  → `confidential_capability()` 恒 `not_configured`（live=False,
  egress=deny）；注册的 double 只列入 `synthetic_adapters`，
  **永不翻 status**。

## 已知限制 / 能力声明

- **恒 `not_configured`**：U08/U09/U11 未决——无 owner 批准的
  provider/account/region/environment，registry 缺批准即拒绝；
  `confidential_capability` 永不伪造 live，double 登记也只入
  `synthetic_adapters`。
- **密钥释放内联重验**：`release_key` 每次自带 attestation 校验——
  调用方 verdict 不被信任（伪造对象无法放闸）；real provider 的
  重验节奏于激活时再定。
- **无真实加密信封**：skeleton 只建 key-release 时序模型（attest→
  release→submit）；payload 的信封加密属真实 provider SDK 接入
  时的绑定项，本票不伪造 crypto。
- **合成证据**：全部证据来自进程内 double；真实 attestation 格式、
  GPU 覆盖报告、保留语义须 provider 实测后填 `ApprovedEnvironment`。
- **残余可观测面**：metadata/timing/size/endpoints 是 provider 恒
  可见的——见 cloud-security.md，不声称抗 compromised guest 或
  全部侧信道。
- **证据驻内存**：receipts/observations 与 broker 同为 in-memory
  设计；落库属 domain 侧后续票据（cs1003 域服务的接续工作）。
